## 一、核心概念与技术对比

### 1.1 什么是"像素授权自动化"？

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   以前（手动）:                                               │
│                                                             │
│   小明打开 fbspider.com                                      │
│       → 找到像素列表                                          │
│           → 找到目标像素                                      │
│               → 填入广告账户 ID                               │
│                   → 点"授权"按钮                              │
│                       → 等待结果                              │
│                           → 再来下一个...                     │
│                                                             │
│   一个一个点，一天点 100 个，手指头都要断了 😫                  │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   现在（自动化）:                                             │
│                                                             │
│   OpenClaw 发一条指令                                         │
│       → 后端自动找到在线的浏览器插件                            │
│           → 插件在 fbspider.com 上自动操作                     │
│               → 结果自动返回                                  │
│                                                             │
│   一秒钟发一个，批量跑，人不用管 😎                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**一句话定义**：把人在 fbspider.com 网站上手动点击授权像素的操作，变成程序自动完成。

### 1.2 与其他自动化技术的对比

```
┌──────────────────┬──────────────────┬──────────────────┐
│   RPA 机器人      │   Selenium       │   本系统          │
│   (如 UiPath)     │   自动化测试      │   (插件+后端)     │
├──────────────────┼──────────────────┼──────────────────┤
│                  │                  │                  │
│  模拟鼠标键盘     │  驱动浏览器       │  直接调 API       │
│  需要桌面环境     │  需要 ChromeDriver│  只需浏览器插件    │
│  速度慢          │  速度中等         │  速度快           │
│  容易被检测       │  容易被检测       │  跟人操作一样      │
│  部署复杂        │  部署中等         │  部署简单          │
│  💰 收费         │  🆓 免费但重      │  🆓 免费          │
│                  │                  │                  │
│  适合: 企业流程   │  适合: 测试       │  适合: 广告投放    │
│                  │                  │                  │
└──────────────────┴──────────────────┴──────────────────┘
```

**本系统的核心差异**：不模拟鼠标键盘，而是直接调用网站背后的真实 API，速度快、稳定性高、不会被检测。

#### ① 浏览器插件 — "手"

```
┌─ Chrome 浏览器 ──────────────────────────────┐
│                                              │
│  ┌─ fbspider.com 页面 ─────────────────┐     │
│  │                                     │     │
│  │   用户已登录 ✅（有 Cookie）          │     │
│  │                                     │     │
│  │   ┌─ content-pixel.js ──────────┐   │     │
│  │   │                             │   │     │
│  │   │  🔗 WebSocket 连接后端      │   │     │
│  │   │  📡 接收授权指令             │   │     │
│  │   │  🚀 调用 fbspider API       │   │     │
│  │   │  📤 上报执行结果             │   │     │
│  │   │                             │   │     │
│  │   └─────────────────────────────┘   │     │
│  │                                     │     │
│  └─────────────────────────────────────┘     │
│                                              │
└──────────────────────────────────────────────┘

插件的关键能力：
  ✅ 自动带着用户的登录 Cookie
  ✅ 能直接调 fbspider 的后台 API
  ✅ 一直在线，随时接收指令
  ✅ 断线自动重连（5秒）
```

#### ② 后端服务 — "大脑"

```
┌─ fbspider-server (47.129.247.139) ──────────┐

│  └─────────────────────────────────────────┘ │
│                                              │
└──────────────────────────────────────────────┘

后端的关键能力：
  ✅ 一个后端服务，多个用户共用
  ✅ 通过 username 区分不同用户的设备
  ✅ 自动路由：指令发给正确的用户插件
  ✅ 异步任务模式：发指令 → 轮询结果
```

#### ③ Skill 封装 — "翻译官"

```
┌─ OpenClaw 调用 Skill ──────────────────────┐
│                                            │
│  OpenClaw 说:                              │
│    "帮我授权像素 123 给账户 456"             │
│         │                                  │
│         ▼                                  │
│  ┌─ Skill (Python 类) ──────────────┐      │
│  │                                  │      │
│  │  翻译成 HTTP 请求:                │      │
│  │  POST /api/open/pixel/authorize  │      │
│  │  Body: { pixel_id: "123",        │      │
│  │         target_account_id: "456"}│      │
│  │                                  │      │
│  │  等结果:                          │      │
│  │  每2秒查一次，最多等60秒           │      │
│  │                                  │      │
│  │  翻译回 OpenClaw 能懂的格式:       │      │
│  │  { success: True,                │      │
│  │    authorized: True }            │      │
│  └──────────────────────────────────┘      │
│                                            │
└────────────────────────────────────────────┘

Skill 的关键能力：
  ✅ 一行代码调授权：skill.authorize(...)
  ✅ 自动轮询等结果，不用手动查
  ✅ 格式化返回值，OpenClaw 直接用
```

## 三、核心优势

### 3.1 优势全景图

```

                    │  核心优势  │
                    └─────┬─────┘
          ┌───────────┬───┴───┬───────────┐
          ▼           ▼       ▼           ▼
     ┌─────────┐ ┌────────┐ ┌────────┐ ┌────────┐
     │ 速度快   │ │ 稳定   │ │ 安全   │ │ 易扩展 │
```

### 3.2 逐项说明

```
┌─ 速度 ─────────────────────────────────────────┐
│                                                │
```

### 4.2 场景详解

#### 场景 1：批量像素授权

```
  以前的痛苦:

  小明有 50 个像素要授权给 10 个账户
  = 50 × 10 = 500 次手动操作
  每次约 30 秒
  = 500 × 30 = 15000 秒 ≈ 4 小时 😫


  现在的方案:

  for pixel_id in pixel_list:          ← 循环 50 个像素
      for account_id in account_list:  ← 循环 10 个账户
          skill.authorize(pixel_id, account_id)

  每次约 3 秒
  = 500 × 3 = 1500 秒 ≈ 25 分钟 😎
  而且不用人盯着
```

#### 场景 2：定时任务

```
  需求: 每天早上 9 点，把新创建的像素授权给指定账户

  ┌─ 定时脚本 ──────────────────────────┐
  │                                     │
  │  # cron: 0 9 * * *                  │
  │                                     │
  │  new_pixels = 获取今天新建的像素      │
  │  for pixel in new_pixels:           │
  │      skill.authorize(               │
  │          pixel_id=pixel,            │
  │          target_account_id=目标账户   │
  │      )                              │
  │                                     │
  └─────────────────────────────────────┘

  人不用管，自动跑，结果记日志
```

#### 场景 3：多账户管理

```

  ┌─────────────────────────────────────────────┐
  │            共用后端 (47.129.247.139)          │

  │   设备表:                                    │
  │   ┌────────────┬──────────────────┐         │
  │   │ 设备 ID     │ 用户名            │         │
```

### 5.2 数据流架构（一次授权的完整路径）

```
  步骤                                              耗时
  ────                                              ────

  ① OpenClaw 调 Skill.authorize()                   ~0ms
       │
       ▼
  ② Skill 发 HTTP POST 到后端                       ~100ms
     POST /api/open/pixel/authorize
     { pixel_id, target_account_id, username }
       │
       ▼
  ③ 后端鉴权 + 找设备 + 生成 task_id                  ~50ms
       │
       ▼
  ④ 后端通过 WebSocket 下发指令给插件                  ~50ms
     { action: "authorize_pixel", params: {...} }
       │
       ▼
  ⑤ 插件收到指令，检查页面，调 fbspider API            ~500-2000ms
     fetch('fbspider.com/api/...', { credentials: 'include' })
       │
       ▼
  ⑥ 插件把结果通过 WebSocket 上报                     ~50ms
     { type: "task_result", result: {...} }
       │
       ▼
  ⑦ 后端缓存结果到内存                                ~0ms
       │
       ▼
  ⑧ Skill 轮询查到结果，返回给 OpenClaw                ~2000ms
     GET /api/open/pixel/result/{task_id}

  ────────────────────────────────────────
  总计约: 3-5 秒
```

### 5.3 设备路由架构（如何找到正确的插件）

```
  用户发起请求时，可以传不同的参数来指定设备:

  ┌─────────────────────────────────────────────────────┐
  │                                                     │
  │  优先级 1: 传 device 参数                            │
  │  ┌───────────────┐                                  │
  │  │ device: "px_ab"│──→ 按设备 ID 前缀精确匹配        │
  │  └───────────────┘   适用: 调试时指定特定设备         │
  │                                                     │
  │  优先级 2: 传 account_id 参数                        │
  │  ┌──────────────────────┐                           │
  │  │ account_id: "act_123"│──→ 广告账户 → 用户 → 设备  │
  │  └──────────────────────┘   适用: 广告操作自动路由    │
  │                                                     │
  │  优先级 3: 传 username 参数  ⭐ 推荐用于像素授权      │
  │  ┌──────────────────────────┐                       │
  │  │ username: "alice@xxx.com"│──→ 用户名 → 匹配设备   │
  │  └──────────────────────────┘   适用: 像素授权场景    │
  │                                                     │
  │  优先级 4: 什么都不传                                │
  │  ┌───────────────┐                                  │
```

### 6.1 实战 1：第一次调用像素授权

```

  返回:
  {

    "data": {

  第二步: 发起授权

  $ curl -X POST http://47.129.247.139:7150/api/open/pixel/authorize \

  第三步: 查结果（等几秒后）

    "status": "done",
```

### 6.2 实战 2：用 Python Skill 一行搞定

```python
  from fbspider_pixel_authorize import FbspiderPixelAuthorize

  skill = FbspiderPixelAuthorize(

      base_url="http://47.129.247.139:7150"

      target_account_id="act_987654321",

```

### 6.3 实战 3：批量授权脚本

```python
  pixels = ["111", "222", "333", "444", "555"]

  results = []
  for pixel in pixels:
```

## 九、常见问题

### Q1: 插件装了但后端看不到设备在线？

```
  排查步骤:

  1. 打开 fbspider.com 页面（插件只在这个页面生效）
  2. F12 → Console，搜索 [Pixel]
  3. 应该看到:
     [Pixel] Content script 已加载, device_id=px_xxx
     [Pixel] WebSocket 已连接          ← 如果没有这行，说明连不上
  4. 如果没有 "已连接":
     → 检查 WS_URL 是否指向 47.129.247.139:7671
     → 检查服务器 7671 端口是否开放
     → 检查防火墙是否放行
```

### Q2: 调接口返回 "Unauthorized"？

```
  原因: API Key 无效或缺失

  检查:
  → 请求头是否带了 X-API-Key
  → Key 格式是否正确（fbk_ 开头）
  → Key 是否已被撤销
  → Key 是否已过期
```

### Q3: 返回 "API Key 缺少 scope: device-control"？

```
  原因: Key 没有像素授权的权限

  解决: 让管理员重新创建一个带 device-control scope 的 Key
```

### Q4: 返回 "用户 xxx 没有在线设备"？

```
  原因: 该用户名对应的插件没有连上后端

  检查:
  → 插件是否已安装
  → 是否在 fbspider.com 页面上
  → Console 是否显示 WebSocket 已连接
  → getUsername() 是否正确提取到了邮箱
```

### Q5: 任务一直 pending，没有结果？

```
  原因: 插件收到指令但执行失败，或者没有返回结果

  检查:
  → 浏览器 Console 看是否有错误
  → Network 面板看 fbspider API 请求是否发出
  → 确认 authorizeViaAPI() 中的接口地址是否正确
```

### Q6: gunicorn 为什么只能 1 个 worker？

```
  因为 WebSocket 的设备列表和任务结果存储在进程内存中:

  ┌─ Worker 1 ─┐    ┌─ Worker 2 ─┐
  │ devices: A  │    │ devices: B  │   ← 两个 worker 的数据不一致!
  │ results: X  │    │ results: Y  │
  └─────────────┘    └─────────────┘

  请求可能被分发到不同的 worker，导致:
  → 找不到设备（设备注册在 Worker 1，请求到了 Worker 2）
  → 找不到结果

  解决: workers = 1（单进程，内存共享）
```
